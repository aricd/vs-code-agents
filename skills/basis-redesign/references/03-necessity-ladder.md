# Stage 03 — Necessity ladder

Contents: [Entry and exit](#entry-and-exit) · [The ladder](#the-ladder) · [Disposition precedence](#disposition-precedence) · [Overlay flags](#overlay-flags) · [Evidence bar](#evidence-bar) · [Keep-vs-fold scorecard](#keep-vs-fold-scorecard) · [Worked examples](#worked-examples) · [Independent passes](#independent-passes) · [Ladder-verdict record](#ladder-verdict-record) · [Reconciling disagreements](#reconciling-disagreements)

For each catalogued construct X this stage asks, in reverse, the admission question of
[`lean-design`](../../lean-design/SKILL.md): does X need to exist, and if it does, can the rest
of the vocabulary carry it? It assigns each construct exactly one disposition plus two overlay
flags, and writes the result as the ladder-verdict record that stage 04 reads.

## Entry and exit

- **Entry:** the catalog is complete and the budget is confirmed. The pilot family is the one
  exception: this stage runs on it first, and the budget is confirmed after the pilot.
- **Exit:** a forward and a reverse pass, reconciled; one disposition and both overlay flags per
  construct; one ladder-verdict record; any guardrail exception approved by the user, naming
  the guarantee.

## The ladder

Every test below is made against the **fixed original full set minus X**, under the declared
composition relation (host-language escape hatches excluded unless declared). Never test against
a set from which other "redundant" constructs were already dropped; removal of several
constructs together is decided only at stage 04.

| Rung | Question | Success means |
|---|---|---|
| 1 | Does X need to exist? Is there any corpus use, or any cited need? | A use or a cited need exists. If neither, X is `Dead` and the ladder stops |
| 2 | Can X be composed from the fixed (full set − X)? | One composition satisfies every atomic behavior of X together, and passes the rung-2 check (see [Evidence bar](#evidence-bar)) |
| 3 | Can X be expressed as a variant of a neighbor, adding no construct? | The neighbor carries X's behaviors; the fold is checked against the keep-vs-fold scorecard where one applies |
| 4 | Keep X | Entered exactly when rung 3 fails |

A rung-2 attempt is in **good faith** only when it is recorded: each composition tried, and the
checklist item (from the stage-02 atomic behaviors) that it fails or that it satisfies. "No
neighbor carries it" without an attempt is not a rung-2 attempt, and a construct with no recorded
attempt cannot be `Essential`.

**Rung-2 check.** A composition is judged by the Run Declaration's rung-2 check: the declared
oracle itself or, when that oracle compares generated bytes, the declared semantic check
(validator equality plus a behavioral probe). `passed` is relative to that check and settles
rung-2 status only; the byte oracle stays the stage-08 gate. When no member of the check reacts
to X (deleting X changes nothing it can see), a pass is vacuous: record the composition with
`oracle_status: unproven` and the note `oracle-blind`. Where nothing composes X, record the
removal itself as a composition whose sole provider is the pseudo-construct of
[stage 04](04-joint-removal.md#input-record). Either way X is `Unproven`, never `Exchangeable`.

**Rung 3 neighbors.** Siblings in the same `group` count as neighbors. The group itself does
not: a variant entry made by the catalog's split is already a variant of its group, so it is
not re-tested as one.

**Lowerings must be injective.** A composition or fold that lowers X to a form of the
remaining set is accepted only after lowering then lifting reproduces every authored document
on the corpus, including documents that already contain the lowered form's literal or token.

## Disposition precedence

The first matching row wins. Read the columns left to right.

| Needed (a use or a cited need)? | Composition with oracle status `passed` | Composition found, none `passed` | Fold succeeds | Disposition | Rung |
|---|---|---|---|---|---|
| No | any | any | any | `Dead` | 1 |
| Yes | at least one | any | any | `Exchangeable` | 2 |
| Yes | none | at least one `unproven` | any | `Unproven` | 2 |
| Yes | none | none (nothing found, or every found composition `failed`) | Yes | `Fold-in candidate` | 3 |
| Yes | none | none (nothing found, or every found composition `failed`) | No | `Essential` | 4 |

Every combination of outcomes lands on exactly one row. A `passed` status needs a check member
that reacts to X; a vacuous pass is `unproven` and never reaches row 2. Details:

- **`Dead`**: no corpus use and no cited need, **regardless of reproducibility**. A Dead
  construct may be irreproducible; it is still Dead. Removing it changes the accepted language,
  so every Dead construct is routed to stage 09.
- **`Exchangeable`**: at least one composition executed under the rung-2 check and `passed`.
- **`Unproven`**: a composition was found but none has `passed`; each is `unproven` (not yet
  executed, or awaiting an oracle). The report says "redundancy unproven — execute to resolve".
  An Unproven construct is never labeled `Essential` or `Fold-in candidate`.
- **`Fold-in candidate`**: nothing composes it, but a neighbor can absorb it as a variant. Stage
  04 never removes it; stage 05 may fold it.
- **`Essential`**: the remainder. Irreproducibility is necessary for Essential but not
  sufficient: it also needs a recorded good-faith rung-2 attempt and a failed fold.
- **A composition that was executed and `failed` counts as not found** for that alternative. It
  stays in the record with status `failed`; it never moves a construct toward `Unproven`.
- Rung 4 is entered exactly when rung 3 fails, so `Essential` and `Fold-in candidate` never both
  apply.

## Overlay flags

Two flags are recorded beside the disposition. They never replace it.

**`guardrail: held | checked-pass(<check citation>) | n/a`**: does a guarantee depend on X?
Source the guarantees through [`requirements-enforcement`](../../requirements-enforcement/SKILL.md)
and record each with its maturity (candidate, plan-local, adopted, formal), and add the
compatibility contract declared at stage 01 and the classes of
[`lean-design` Guardrails](../../lean-design/SKILL.md#guardrails--never-simplify-away).

- `held`: a guarantee of maturity plan-local or above depends on X and no check shows a
  replacement preserves it. A ledgered candidate-maturity guarantee generates no obligation of
  its own; record it and show it to the user at the checkpoint instead of silently holding or
  ignoring it. The exception is a rule the code enforces that no ledger lists: surfaced as a
  candidate guarantee at stage 01, its construct is `held` until the user decides.
- `checked-pass(<citation>)`: a check shows the guarantee still holds without X (a test, an
  invariant, an approved exception); cite it. A user-approved exception names the guarantee.
- `n/a`: no guarantee touches X; say what was searched.

**`keep: depth(<scorecard citation>) | none`**: keep a *composable* construct because removing
it would leave callers with a shallower interface. Example: a composable `partition` operator
kept because the composed form costs every caller more required knowledge. `depth(...)` needs a
citation of the scorecard that shows it; without one, the value is `none`.

Both flags feed stage 04: guardrail `held` and keep `depth` put the construct in every candidate
remaining set.

## Evidence bar

A composition supports removal only if it was **executed under the rung-2 check and
`passed`**. A composition that was found but has not passed yields `Unproven`. Compositions are
executed at this stage under every `equivalence_strength`; the strength changes only what stage
04 admits and which verdicts may later be final. Each composition carries an `evidence_id`
pointing at the run, test or artifact that shows its status, so a reviewer can re-run it.
Execution uses the stage-01 rung-2 check and pinned baseline; with `oracle: none` there is no
rung-2 check, and nothing can reach `passed`.

## Keep-vs-fold scorecard

Wherever a keep-or-fold comparison exists, a [`deep-modules`](../../deep-modules/SKILL.md)
scorecard compares the two shapes: construct kept as is, versus folded or composed. This applies
to every `keep: depth(...)` claim and to every fold that adds caller-visible surface (a
parameter, a mode flag, a new error the caller must handle). A fold that adds none needs no
scorecard. Lint any file that contains a scorecard with `scripts/validate-scorecard.ps1`.

## Worked examples

**1. Mutual-cover pair.** `map_values` can be written with `for_each_entry` and a collector;
`for_each_entry` can be written with `map_values` and an identity transform. Each has a passed
composition against the *fixed* full set (which includes the other), so both are `Exchangeable`.
Removing both would lose the capability; that is why the ladder only labels and stage 04
decides jointly. Records: `map_values` alternatives `[{for_each_entry, collect}]`,
`for_each_entry` alternatives `[{map_values}]`, both `passed`.

**2. {NAND} versus {AND, NOT}.** In a vocabulary of `NAND`, `AND` and `NOT`: `NAND` composes
as `NOT(AND(a, b))` (alternative `{AND, NOT}`); `AND` and `NOT` each compose from `NAND`
alone (alternatives `{NAND}`). All three are `Exchangeable`. Two irredundant bases exist,
`{NAND}` and `{AND, NOT}`, of different size. The ladder does not pick; stage 04 reports both.

**3. Dead, irreproducible.** `legacy_retry` has zero corpus uses and no cited need, while its
IR node and generator code still exist. No composition reproduces its retry-state handling, and
no neighbor can absorb it. Precedence row 1 applies first: `Dead`, rung 1, routed to stage 09.
It is not `Essential`, because reproducibility is never consulted for a construct nobody uses.

**4. Unproven.** `window_sum` has a candidate composition, `fold` over `slice`, found by a
pass but not yet executed under the oracle. No composition has `passed`. Disposition:
`Unproven`, rung 2; the report says "redundancy unproven — execute to resolve". It is not
`Essential`: the composition exists. Under `hard` it is forced into every remaining set at stage
04; under `advisory` stage 04 may propose removing it, labeled `output-unverified`.

## Independent passes

Run the procedure of
[`deep-modules-interface-cost-audit` Step 3](../../deep-modules-interface-cost-audit/SKILL.md#step-3--the-audit-unit-6-delegations-repeated-once-per-batch):
a forward pass, a reverse pass, a critique of each, and a reconciliation, once per batch from
stage 02. That section owns the delegation mechanics, the critique annotations and the
Reconciliation Guardrail (never introduce an adjusted number that is not derived and reconciled
against any tabulated number); this stage adds only the rules below.

- **Blind.** The forward pass receives the catalog in order, the reverse pass receives it in
  exact reverse order. Neither is shown the other's output, nor a draft record.
- **No nested delegation.** When the executor cannot delegate, run the passes one after
  another as separate passes by that one executor, each from the Run Declaration and catalog
  alone, without reading the other's output until reconciliation. Record a weakened-blindness
  note in the stage evidence, and count the budget in passes, not delegations.
- **Same inputs, same record.** Each pass gets the Run Declaration, the catalog with atomic
  behaviors, the fixed full set and the oracle details, and emits one ladder-verdict record.
- **Critiques verify, they do not rewrite.** A critic re-runs any `passed` composition it
  doubts and checks every `Dead` claim against the stage-02 query, marking each item
  `confirmed`, `rejected` or `not_reviewed`.

## Ladder-verdict record

One JSON file per run, schema version `1`. It is also the alternatives record that stage 04
consumes (see [04-joint-removal.md](04-joint-removal.md#input-record)).

```json
{
  "schema_version": 1,
  "in_scope": ["NAND", "AND", "NOT"],
  "transitive": true,
  "equivalence_strength": "hard",
  "limit": 20,
  "constructs": [
    {
      "uid": "NAND",
      "disposition": "Exchangeable",
      "rung": 2,
      "overlays": { "guardrail": "n/a", "keep": "none" },
      "evidence": ["rung-2 attempts: NOT(AND(a, b)); checklist items 1-4 hold"],
      "alternatives": [
        { "providers": ["AND", "NOT"], "evidence_id": "run-0412", "oracle_status": "passed" }
      ]
    }
  ]
}
```

| Field | Content |
|---|---|
| `schema_version` | `1` |
| `in_scope` | Every in-scope construct uid |
| `transitive`, `equivalence_strength` | Copied from the Run Declaration; a mismatch is a defect |
| `limit` | Exhaustive-search limit for stage 04 (default 20) |
| `uid` | Catalog uid |
| `disposition`, `rung` | `Dead`/1, `Exchangeable`/2, `Unproven`/2, `Fold-in candidate`/3, `Essential`/4 |
| `overlays` | `guardrail`: `held`, `checked-pass(<citation>)` or `n/a`; `keep`: `depth(<citation>)` or `none` |
| `evidence` | Citations: rung-2 attempts, corpus-use query, fold check, scorecard |
| `alternatives` | Each: `providers` (one AND-set of uids), `evidence_id`, `oracle_status` (`passed`, `failed`, `unproven`). One alternative is one composition that satisfies all of X's atomic behaviors together |

An `Exchangeable` construct has a `passed` alternative; an `Unproven` one has an `unproven`
alternative and no `passed`; `Fold-in candidate` and `Essential` have only `failed` ones, or
none. Stage 04 refuses a record that breaks these rules.

## Reconciling disagreements

Reconcile per construct, by the rule for the disagreement. Record every non-agreed item with a
status and a resolution note; never split the difference.

| Disagreement | Rule |
|---|---|
| Same disposition, different alternatives | Union them. Each keeps its own `evidence_id`; identical AND-sets merge |
| One pass found a composition, the other did not | Existence is decided by execution, not by count. Execute it: `passed` makes `Exchangeable`, `failed` is recorded and the construct falls to the next row, not yet executable gives `Unproven` |
| `Exchangeable` versus `Unproven` | Decided only by the oracle status of the evidence. Re-check the `evidence_id` run; a `passed` with no re-checkable run is `unproven` |
| `Dead` versus needed | Re-run the stage-02 corpus query. Any use or cited need makes it not Dead; a query that could miss uses cannot establish zero |
| `Fold-in candidate` versus `Essential` | Attempt the fold. If it adds caller-visible surface, run the scorecard. If it stays disputed, record `Essential` (the stricter claim) and list it as an open question for the user |
| `guardrail` differs | `held` stands unless the other pass cites a check the reconciler re-verifies, or the user approves an exception naming the guarantee |
| `keep` differs | `depth(...)` stands only with a scorecard citation the reconciler can read; otherwise `none` |

After reconciliation the record is complete: every in-scope construct has one disposition, both
flags and its alternatives. At the checkpoint, ask the user to approve any guardrail exception,
naming the guarantee, before stage 04 runs.
