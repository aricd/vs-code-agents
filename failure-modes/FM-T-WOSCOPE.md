# FM-T-WOSCOPE

This class file did not previously exist -- `failure-modes/INDEX.md` carried the mode's only recorded instance (`.001`) as a compressed one-line description with no dedicated file. Created 2026-09-24 when two new, mechanically distinct instances were observed in a downstream consumer repo, following the same file-per-class convention already established by `FM-T-OPENQGATE.md`.

## Mode: FM-T-WOSCOPE.STAT-TRUNCATION

**Mechanism.** A file-scope check that parses `git diff --stat`'s own human-display output to recover changed paths inherits `--stat`'s column-width truncation of long paths (git abbreviates with a leading `...` to fit a fixed terminal width). A path recovered in this truncated, ellipsis-prefixed form fails a literal/prefix comparison against `scope.allowed_files`, producing a false "out-of-scope" flag on a path that is genuinely declared allowed. This is the mechanism `G-T-WOSCOPE`'s own wording anticipates ("independent of git's display abbreviation").

**Oracle.** `--` (provisional; no dedicated oracle wired for the divergent implementation this mode's new instance was found in -- see Instance `.002` note). The canonical `scripts/run-work-order-gates.ps1`/`.sh` already avoid this mechanism entirely (they use `git diff --name-only $BaseCommit`, never `--stat`, precisely to avoid it -- see that script's own inline comment at the diff-collection site), so `scripts/test-property-oracle.ps1` validates the canonical implementation is not exposed to this mechanism, but does not (and structurally cannot, without being pointed at it) validate a downstream repo's own divergent reimplementation.

## Mode: FM-T-WOSCOPE.STALE-BASE-DIVERGENCE

**Mechanism.** A file-scope check that diffs against a fixed ref (`HEAD`) rather than the work-order's own `meta.base_commit` cannot distinguish this delegation's own changes from any OTHER already-dirty, uncommitted content already sitting in the working tree at delegation start (e.g. a sibling in-flight plan's own not-yet-committed artifacts). Every such pre-existing dirty path is then evaluated against THIS delegation's `scope.allowed_files` and flagged as out-of-scope, even though the delegation never touched it. The canonical `scripts/run-work-order-gates.ps1`/`.sh` already read `meta.base_commit` from the work-order YAML for exactly this reason (see that script's own inline comment: "a moving HEAD anchor would make anything committed mid-delegation invisible to the diff and the scope check would pass vacuously" -- the inverse failure this mode names is the inverse of that stated concern: a NON-moving, HEAD-hardcoded anchor in a working tree that already has unrelated dirty content produces a false FAIL instead).

**Oracle.** `--` (provisional; not yet wired for the divergent implementation this instance was found in).

Running Plan 063's own work-order gate against a working tree that ALSO had ~35 unrelated, already-dirty files from 3 separate in-flight sibling plans (011, 070, and several standalone analysis/architecture/critique docs) present BEFORE Plan 063's own delegation began, flagged all ~35 of them as `ERROR: out-of-scope file: ...` alongside the 2 genuine findings (see `.STAT-TRUNCATION.002`). Independently confirmed via a `git status --short` snapshot taken BEFORE the delegation started, showing the identical file list already modified/untracked. In this specific instance `base_commit` (`bee75db`) happened to equal `HEAD` (nothing had been committed since), so using `--name-only $BaseCommit` per the canonical script's own pattern would not itself have excluded the pre-existing dirty files either -- the deeper, still-open finding is that a file-scope check run mid-way through a multi-plan orchestration session with several plans' artifacts sitting uncommitted in the same working tree cannot cleanly attribute a "whose change is this" question from git state alone; the canonical script's own `base_commit`-anchored design mitigates the DIFFERENT failure (a moving HEAD across commits), not this one (a static, shared, multi-plan-dirty tree). |

**Disposition (this instance only, not a registry-level fix).** The orchestrating Planner accepted this instance as environmental noise for Plan 063's own acceptance (independently re-verified the real diff was in-scope via `git diff --name-only $BaseCommit -- <allowed roots>` + `git ls-files --others --exclude-standard`, scoped by hand to the allowed roots) rather than blocking the plan on it. This does not close the underlying mode -- see the open question in Related, below.
